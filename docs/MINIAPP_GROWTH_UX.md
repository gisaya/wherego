# 주말어디 미니앱 UX 보완

## 이번 수정

- 기존 사진·색상·선택지와 AI 결과 화면은 유지한다. 현재 추천은 원천 3개·일반 3개, 총 6문항이다. 첫 화면은 주말 목적과 6가지 선택을 명확히 한다.
- 결과의 주요 행동에 친구에게 장소 공유를 추가한다. SDK `getTossShareLink`와 `share`를 사용한다. 받은 사람은 미니앱에서 같은 장소 이름·주소를 보고, 지도를 열거나 찜하거나 자기 추천을 시작한다.
- 공유 데이터는 공개 장소 이름·주소·지역만 허용한다. 출발 위치, 선택 답변, AI 개인화 설명, 사용자·세션 식별자는 포함하지 않는다. 공유 내용은 수신자가 바꿀 수 있는 공개 데이터이므로 검증된 AI 추천으로 표현하지 않는다.
- 찜은 앱 저장 공간에 최대 20곳을 보관한다. 삭제·중복 방지·손상 데이터 복구를 지원한다. 장소 재열람·지도 열기는 AI 추천 API를 호출하지 않는다. 새 추천은 기존 이용 횟수와 광고 정책을 따른다.
- 질문마다 배너를 재생성하지 않는다. 빈 광고·표시 오류는 해당 추천 흐름에서 접으며 반복 재요청하지 않는다. 배너는 질문 버튼 위에 겹치는 절대 위치 대신 화면의 별도 하단 영역에 둔다.
- 매일 첫 기본 추천과 이용권 경로는 광고 없이 제공한다. 리워드 광고는 SDK의 `userEarnedReward`와 `dismissed`를 확인하며 보상 크레딧에는 두 번째 전면광고를 표시하지 않는다. 기존 공유 크레딧 등 전면광고 경로는 `impression`과 `dismissed`를 확인한다. 미지원·표시 실패·응답 지연을 성공으로 취급하지 않는다.
- 광고 실패 시 답변과 추천 세션·준비 후보를 유지하여 광고 재시도를 제공한다. 광고 확인 이후의 AI 오류 재시도는 유지한다. 무료·광고 횟수는 아래 새 정책으로 변경했고 광고 ID·가격·프로모션 정책은 유지한다.

## 매일 첫 무료와 무제한 광고 추천

2026-10-01 사용자 요청에 따라 서버와 미니앱을 함께 수정했다. 정책·프롬프트 서버 `3a52c4e`는 배포를 확인했다. 광고 중 비공개 준비 API의 `b9636cc`는 origin/main에 fast-forward 푸시했고 Render health의 gitCommit 일치로 배포를 확인했다. [Server QC](https://github.com/gisaya/jbg/actions/runs/36803383613)도 성공했다. 앱 흐름 변경은 아래 최신 AIT 상태를 따른다.

- KST 매일 첫 기본 추천 1회는 광고 없이 제공하며, 질문·로딩·결과 배너도 숨긴다.
- 이후 광고 시청 완료마다 추천 1회가 추가되고 일일 광고 횟수 제한은 없다. 결과 조회에는 실제 획득한 크레딧이 필요하다. 아래 20초 비공개 준비는 보상 전 AI 비용을 감수하는 사용자 승인 예외이며 무료 결과나 가짜 광고 크레딧을 지급하지 않는다.
- `baseDailyLimit: 1`, `adRewardsLimit: null`을 서버가 반환한다. 잔여 횟수는 실제 획득한 크레딧만 표시하고 공유·유료 이용권·실패 환불·중복 세션 처리는 유지한다.
- 중복 보상·종료/실패한 광고의 지연 이벤트는 크레딧을 다시 지급하지 않는다. 질문 답변 후 크레딧이 부족해 광고를 시청한 경우 같은 6개 답변으로 이어간다.
- 결과의 친구 공유 버튼 위에 16px 여백을 추가하고 안내는 `장소 이름과 주소만 공유해요.` 한 줄로 줄였다. 작은 화면/큰 글씨는 한 줄 폰트 조정도 적용했다. 공유 데이터 범위는 그대로다.
- 새 AIT는 사용량 응답을 받는 API에 `usagePolicy=uncapped-v1`을 보내 `null` 한도를 사용한다. 이전 AIT에는 실제 제한이 아닌 다음 광고 허용 수치(`max(2, adRewardsUsed + 1)`)와 `adRewardsUnlimited: true`를 반환한다. 정상/사용량 오류 응답 모두 Wherego 전용 호환 경로로 처리하며 DB·환경변수 변경은 없다.

광고 완료 이벤트는 SDK 기준이며 서버 측 광고 정산 검증을 새로 추가한 것은 아니다. 무제한 광고 정책의 실제 손익과 오용 여부는 운영 로그·광고 실수령액을 대조해야 한다.

## 신규 결제 제거와 광고 대기 복구

2026-10-01 사용자가 결제 화면으로 보이는 어두운 화면 정지를 보고한 뒤 신규 판매 UI·상품 조회·`appLogin`·`IAP.createOneTimePurchaseOrder` 호출을 제거했다. 캡처만으로 정지 원인을 확정하거나 SDK 모달을 강제로 닫을 수 있다고 보장하지 않는다.

- 일반/혜택 첫 화면과 횟수 화면에 구매 카드·가격·로그인 후 구매 버튼이 없다. 일반 사용자 초기 진입에서는 IAP 상품 API나 네이티브 상품 목록도 조회하지 않는다.
- 서버 상품 응답은 `enabled: false`로 신규 판매를 중단한다. SKU와 기존 지급/환불 API는 보존하고 `restorationEnabled`로 기존 주문 복원 가능 여부를 따로 반환한다. 기존 AIT의 이미 진행 중인 결제를 취소하는 기능은 아니다.
- 보유 유료 크레딧은 광고 없이 그대로 사용할 수 있다. 유효한 저장 로그인 세션이 있으면 기존 미지급 주문 복원과 환불 정합성 확인을 유지한다. 로그인 만료·기기 변경은 자동 재로그인하지 않으며 약관의 기존 이용권 문의 경로를 안내한다.
- 보상 광고 로드 콜백은 15초, 광고 시작 이벤트는 8초까지 기다린 뒤 오류/재시도로 복구한다. `show`/`impression`을 받으면 시작 타이머를 해제하므로 이미 재생 중인 광고 길이를 제한하지 않는다.
- 전용 리워드 광고 그룹은 유지하며 실제 `userEarnedReward`에서만 +1회 지급한다. `show`/`impression`/`dismissed`나 짧게 닫힌 것만으로 지급하지 않는다. 광고 소재 길이와 실제 정산액은 이 테스트에서 검증되지 않았다.
- 광고 실패/시간 초과 이후 지연 콜백과 중복 보상은 무시한다. 로딩 중 언마운트와 화면 이동에서도 콜백·타이머를 정리한다.

서버의 신규 판매 중단·무제한 광고 정책은 배포됐다. 토스 콘솔 상품 상태 및 광고 그룹의 보상형 등록·실제 보상/정산은 실기기에서 별도 확인한다. 광고 ID·모델·프로모션·DB·환경변수는 바꾸지 않았다.

## 질문 완료 후 광고와 결과 준비

- 일반/혜택 첫 화면에서는 잔여 0회여도 출발지와 6문항부터 선택한다. 첫 화면의 광고 충전 버튼을 제거했다.
- 여섯 답변을 고른 뒤 크레딧이 없으면 답변을 유지한 광고 버튼을 표시한다. 광고는 사용자가 누를 때만 열며 일일 첫 무료 추천은 그대로 광고 없이 제공한다.
- 크레딧이 없으면 마지막 답변 직후 `previewOnly: true`로 공공데이터 후보를 준비한다. 이 경로는 AI·이용권 예약·차감·환불 없이 후보만 반환한다. 크레딧이 있는 기존 후보 준비 경로는 그대로다.
- SDK `impression`에서만 20초 타이머를 시작한다. `requested`·`show`는 타이머를 시작하지 않는다. 20초 뒤 광고가 열려 있고 보상이 아직 없으면 `/api/wherego/prepare-selection`으로 Gemini 선택을 서버에 비공개로 준비한다. 해당 API는 준비 상태만 반환하며 장소·설명·보상·크레딧은 반환하지 않는다.
- SDK `userEarnedReward`가 먼저 오면 타이머를 취소한다. 서버 크레딧 지급 확인 직후 추천을 시작하므로 짧은 광고를 20초까지 기다리게 하지 않는다. 이미 비공개 준비를 시작한 경우 같은 선택을 재사용하며, 결과 이미지도 정식 응답 직후 미리 불러온다.
- `dismissed` 전에는 결과 화면으로 이동하지 않는다. 닫힌 뒤 이미 준비됐으면 즉시 결과를 표시하고, 준비 중이면 AI 로딩을 표시한다. 보상 이벤트가 광고 끝에서만 오면 광고 중 준비 시간이 짧을 수 있어 즉시 결과를 보장하지 않는다.
- 공식 `showFullScreenAd`는 남은 시간/영상 길이 이벤트를 제공하지 않는다. 20초는 노출 이벤트 이후 경과 시간이지 광고 종료 5초 전이나 실제 연속 시청 시간의 증명이 아니다. 종료·실패·홈 이동·언마운트에서 타이머를 취소한다. 보상·서버 지급 실패 시 준비 결과를 공개하지 않는다.
- 서버 준비는 사용자·추천 세션·출발지·답변·후보에 묶인 프로세스 내부 10분 캐시다. 동일 요청의 준비와 정식 추천은 같은 작업을 기다린다. 사용자/날짜/획득 광고 수 기준 미확정 준비는 한 번만 허용하고, 동시 사전 준비 4개·캐시 64개·당일 준비 예산 키 4,096개로 제한한다. 준비가 제한되면 광고 보상 후 기존 추천을 실행한다. 광고 보상 횟수 자체의 상한은 아니다.
- 20초 뒤 AI가 시작된 후 광고를 닫으면 결과를 받지 않아도 API 비용이 발생할 수 있다. 캐시가 만료되거나 서버가 재시작/재배포되면 준비 결과는 사라져 정식 추천에서 AI가 다시 실행될 수 있다. 여러 프로세스/인스턴스 간 중복 방지는 제공하지 않는다. SDK 노출은 서버가 독립 검증한 정산 증거가 아니므로 실제 호출 원가와 광고 실수령액을 대조한다.
- 이전 유한 상한이 화면에 남으면 `최신 추천 횟수 확인`으로 서버를 재조회해 광고를 복구한다. 선택 답변은 유지한다. 재시도와 화면 이탈 후 지연 응답도 회귀 테스트로 확인한다.

## 범위와 제한

- 상황별 버튼을 누르면 관련 질문을 생략하는 기능은 이번에 넣지 않았다. 서버 질문 구성과 답변 점수까지 연결하지 않은 장식용 버튼을 추가하지 않는다.
- 찜은 전체 AI 설명의 재현이나 최근 추천 자동 기록이 아니라, 명시적으로 저장한 공개 장소 목록이다. 과거 거리·시간·혼잡도는 다시 보여주지 않아 현재 정보로 오해하지 않도록 한다.
- 클라이언트 광고 확인은 정산된 광고 수익의 증명이 아니다. 서버 추천 API의 광고 검증·요청 제한까지 새로 설계한 것은 아니다.
- 기존 크레딧 사용 경로의 후보 준비 API는 이용 횟수를 예약한다. 잔여 0회인 광고 경로만 공개 후보 미리보기를 사용하고, 실제 보상 획득 후 정식 추천에서 예약/확정한다. 광고 재시도 시 같은 답변·후보·추천 세션을 유지한다. 앱 종료 후 답변 복구는 별도 검토 항목이다.
- 첫 웹 실험의 AI 미사용 구조는 그대로다. 토스 미니앱과 공개 웹 디자인을 통합하지 않았다.

## 핵심 지표 연결

2026-10-01 빌드에 SDK의 공개 `Analytics.Press`·`Analytics.Impression`을 다시 연결했다. 로깅 컨텍스트가 없으면 원래 화면·버튼으로 복귀하고, 클릭의 원래 행동을 먼저 수행해 SDK 로깅 예외가 지도·저장·공유를 막지 않도록 한다. 컨텍스트 누락·로깅 실패·중복 행동 방지 회귀 테스트를 포함한다. UI와 질문·선택지는 바꾸지 않는다.

코드 연결과 AIT 빌드는 끝났고 사용자가 앱 실기기 검증·토스 버전 등록 완료를 보고했다. 핵심 지표 콘솔 설정과 실제 이벤트 수집 완료까지 보고된 것은 아니다. 보호 경로가 동작하면 앱은 계속 사용할 수 있으나 그 이벤트는 누락될 수 있다. 실제 수집을 확인하기 전 전환율을 신뢰하지 않는다. 커스텀 파라미터는 이벤트 이름뿐이며 답변·출발 위치·사용자 식별자를 추가하지 않는다. SDK가 자동 부여하는 기본 파라미터는 별도다.

- 활성: `weekend_result_view`
- 대표 전환: `weekend_map_click` OR `weekend_saved_place_map_click`
- 공유 행동: `weekend_place_share_click`; 실제 공유 유입은 `weekend_shared_place_view`와 분리해서 본다.
- 찜 행동: `weekend_place_bookmark_click`; 이미지 저장의 `weekend_card_save_click`과 구분한다.
- 찜 재열람: `weekend_saved_places_view`

클릭 이벤트는 실제 공유 완료·예약·방문·저장 성공을 뜻하지 않는다. 찜/공유 지표는 실제 사용량을 보고 콘솔 보조 전환에 선택적으로 연결하며 수익 지표도 별도로 유지한다.

[공식 React Native 계측 문서](https://developers-apps-in-toss.toss.im/documentation/common/growth/analytics/user-behavior)에 따라 QR·샌드박스에서는 운영 분석 데이터가 수집되지 않으며, 출시 데이터는 다음 날 확인한다. QR에서는 앱 동작·개발 로그를 점검하고 운영 배포 후 수집 여부를 따로 확인한다.
